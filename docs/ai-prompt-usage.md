# ARTEMIS2026 AI 프롬프트 활용 기록

> 기준일: 2026-09-06
>
> 목적: ARTEMIS2026 개발 과정에서 AI 도구를 어떤 방식의 프롬프트로 활용했는지 제출용 문서 형태로 정리한다.
>
> 작성 기준: 실제 대화의 의도와 작업 방식은 유지하되, 공식 문서에 적합하지 않은 비속어, 감정적 표현, 지나치게 구어적인 표현은 제외하거나 순화했다.

## 1. 활용 개요

ARTEMIS2026 개발에서는 AI를 단순 코드 생성 도구가 아니라 기획 정리, 구현 보조, 디버깅, 문서화, 에셋 제작 보조, QA 기준 정리에 함께 사용했다. 프롬프트는 대부분 완성된 명령문보다 현재 문제, 원하는 결과, 지켜야 할 제약을 함께 설명하는 방식으로 작성했다.

주요 사용 방식은 다음과 같다.

- 기획 아이디어를 게임 규칙과 문서 구조로 정리
- Unity C# 코드 구현과 기존 코드 수정
- 로켓 발사 물리, 미션 판정, UI 흐름의 요구사항 구체화
- 오류 원인 분석과 수정 방향 요청
- AI 생성 에셋 제작을 위한 이미지·모델 프롬프트 정리
- 최종 제출용 문서와 발표 자료 문장 정리

## 2. 프롬프트 작성 원칙

프롬프트는 다음 원칙으로 작성했다.

1. 원하는 결과를 먼저 말했다.
2. 프로젝트의 현재 상태와 제약을 함께 제공했다.
3. 기존 구조를 유지하고 최소 수정으로 해결하도록 요구했다.
4. 기능이 실제로 동작하는지 확인할 방법까지 요청했다.
5. 제출 문서용 내용은 과장하지 않고 실제 활용 내용을 기준으로 정리하도록 요청했다.

예를 들어 단순히 "로켓 게임 만들어줘"라고 요청하지 않고, "Unity 프로젝트에서 연구한 엔진으로 로켓을 조립하고 실제 물리 발사 결과로 미션 성공을 판정하는 구조를 만들어줘"처럼 목표와 판정 기준을 함께 제시했다.

## 3. 기획 정리용 프롬프트

초기 기획 단계에서는 게임의 핵심 루프, 플레이어 행동, 미션 진행 구조를 문서화하기 위해 AI를 사용했다. 아이디어를 바로 구현하기보다 먼저 게임 규칙과 범위를 고정하는 데 집중했다.

사용한 프롬프트 유형은 다음과 같다.

```text
2018년부터 2026년까지 우주개발 프로젝트를 운영하는 게임을 만들고 싶다.
플레이어는 엔진을 연구하고 로켓을 조립한 뒤 테스트 발사를 한다.
48시간 게임잼 범위에 맞게 핵심 게임 루프, 자원 구조, 미션 진행 방식을 정리해줘.
```

```text
발사 결과가 단순 확률로 정해지는 방식은 피하고 싶다.
플레이어가 배치한 엔진, 방향, 작동 시간이 Unity 물리에 반영되고,
실제 비행 결과로 미션 성공 여부가 결정되도록 기획 문서를 수정해줘.
```

```text
현재 기획 문서에서 구현자가 반드시 지켜야 할 규칙과
나중에 바꾸면 안 되는 조건을 별도 문서로 정리해줘.
```

이 방식으로 게임의 핵심이 "연구-설계-발사-결과 확인-다음 미션 해금"으로 정리되었다. 또한 발사 전 결과를 미리 정하지 않고 실제 시뮬레이션 결과를 기준으로 판단한다는 원칙을 문서에 고정했다.

## 4. 구현 보조용 프롬프트

구현 단계에서는 AI에게 전체 코드를 새로 만들게 하기보다, 기존 Unity 프로젝트의 파일 구조와 클래스 역할을 읽고 필요한 부분만 수정하도록 요청했다.

사용한 프롬프트 유형은 다음과 같다.

```text
현재 Unity 프로젝트 구조를 먼저 확인하고,
로켓 설계 UI에서 엔진 프리셋을 선택한 뒤 위치와 방향을 설정할 수 있게 해줘.
기존 네임스페이스와 asmdef 경계를 유지하고, 변경 범위는 작게 가져가줘.
```

```text
발사 버튼을 누르면 현재 설계값을 읽어 로켓에 힘을 적용하고,
비행 텔레메트리를 수집해서 미션 조건을 평가하는 흐름을 만들어줘.
성공 여부는 실제 비행 상태를 기준으로 해야 한다.
```

```text
이전 미션을 성공했을 때 다음 미션이 열리게 해줘.
단, 같은 결과가 두 번 적용되어 자원이나 해금이 중복 처리되지 않도록 막아줘.
```

```text
기존 코드에 남아 있는 과거 결과 모델과 새 물리 기반 결과 모델이 충돌하지 않게
호환 지점을 확인하고 필요한 부분만 연결해줘.
```

이런 프롬프트는 구현 범위를 좁히고, 기존 프로젝트 구조를 보존하면서 필요한 기능을 추가하는 데 사용했다.

## 5. 디버깅 및 수정 요청 프롬프트

개발 중 발생한 문제는 증상, 기대 동작, 관련 파일 또는 화면 흐름을 함께 설명하는 방식으로 전달했다. AI에게 바로 추측 수정을 맡기기보다 원인 확인 후 수정하도록 요구했다.

사용한 프롬프트 유형은 다음과 같다.

```text
발사 결과 화면에서 미션 성공 표시와 실제 텔레메트리 값이 맞지 않는다.
결과 생성, 미션 평가, UI 표시 순서를 확인해서 원인을 찾아줘.
수정 후에는 같은 발사 결과가 중복 적용되지 않는지도 확인해줘.
```

```text
엔진 스탯이 UI에는 표시되지만 실제 발사 물리에 반영되지 않는 것 같다.
프리셋 데이터, 설계 저장값, 발사 시뮬레이션 적용 지점을 추적해서 고쳐줘.
```

```text
문서에 적힌 규칙과 현재 코드 동작이 다른 부분을 찾아줘.
문서의 목표 구조를 기준으로 수정해야 할 항목을 정리해줘.
```

이 방식으로 단순 오류 수정뿐 아니라 데이터 흐름과 문서 요구사항 사이의 불일치를 확인했다.

## 6. UI 및 사용성 개선 프롬프트

UI 작업에서는 화면에서 플레이어가 무엇을 보고 판단해야 하는지 중심으로 요청했다. 장식적 화면보다 게임 진행에 필요한 정보 표시를 우선했다.

사용한 프롬프트 유형은 다음과 같다.

```text
로켓 설계 화면에서 플레이어가 엔진 성능, 비용, 방향, 작동 시간을 한 번에 확인할 수 있게 정리해줘.
화면은 과하게 꾸미지 말고 게임 진행에 필요한 정보가 잘 보이게 해줘.
```

```text
발사 후 결과 화면에 성공 여부, 실패 사유, 고도, 속도, 체류 시간 같은 실제 텔레메트리를 보여줘.
예측 점수나 임의 등급은 표시하지 말아줘.
```

```text
미션 선택 화면에서 잠긴 미션과 열린 미션이 구분되게 하고,
이전 미션 성공으로 다음 미션이 열리는 흐름이 명확하게 보이게 해줘.
```

이런 요청을 통해 UI가 게임 규칙을 설명하는 보조 장치가 아니라 실제 플레이 판단에 필요한 정보판 역할을 하도록 조정했다.

## 7. 에셋 제작 보조 프롬프트

아트와 3D 모델 제작 과정에서도 AI를 활용했다. 이때는 결과물이 Unity에서 바로 쓰일 수 있도록 형태, 분위기, 해상도, 용도, 파일 성격을 구체적으로 제시했다.

사용한 프롬프트 유형은 다음과 같다.

```text
레트로 우주개발 연구실 분위기의 작업대 3D 오브젝트가 필요하다.
낮은 폴리곤 수, Unity에서 쓰기 쉬운 단순한 형태, 약간 낡은 금속과 목재 질감으로 만들어줘.
```

```text
로켓 엔진 프리셋용 3D 모델을 만들어줘.
각 엔진은 출력형, 냉각형, 안정형, 종합형이 구분되어야 한다.
실루엣만 봐도 차이가 나게 해줘.
```

```text
실패 결과 화면에 사용할 도장 느낌의 픽셀 아트 이미지를 만들어줘.
게임 분위기에 맞게 붉은색 경고 느낌은 살리되 화면을 과하게 가리지 않게 해줘.
```

AI 생성 에셋은 그대로 최종 품질로 확정하기보다 Unity 프로젝트에 넣은 뒤 크기, 머티리얼, 배치, 시인성을 다시 확인하는 방식으로 사용했다.

## 8. 문서화 및 제출 자료 프롬프트

최종 문서 작업에서는 실제 개발 내용을 제출 양식에 맞게 정리하는 데 AI를 사용했다. 특히 GDD, AI 구현 인수인계, QA 기준, 발표 대본, AI 기술 활용 문서 정리에 활용했다.

사용한 프롬프트 유형은 다음과 같다.

```text
현재 프로젝트 문서를 기준으로 게임 소개와 개발 의도를 제출용 문서 문체로 정리해줘.
기획 의도, 핵심 시스템, 조작 흐름, 차별점을 포함해줘.
```

```text
AI 구현 인수인계 문서를 만들어줘.
다른 구현자가 읽어도 발사 처리 순서, 미션 평가 계약, 결과 적용 규칙을 알 수 있게 정리해줘.
```

```text
AI 기술 활용 문서에 넣을 수 있도록,
우리가 개발 중 어떤 방식의 프롬프트를 사용했는지 정리해줘.
공식 문서에 맞지 않는 거친 표현은 제외하고,
실제 개발 방식은 과장하지 말고 써줘.
```

문서화 프롬프트에서는 "보기 좋게 포장"보다 "실제 개발에서 AI가 맡은 역할을 정확히 설명"하는 방향을 우선했다.

## 9. 반복 개발 방식

프롬프트는 한 번에 완성된 결과를 얻기보다 다음 순서로 반복했다.

1. 목표 기능 또는 문서 목적 제시
2. AI가 기존 파일과 구조를 확인
3. 초안 또는 구현안 생성
4. 프로젝트 규칙과 맞지 않는 부분 수정 요청
5. 실행, 빌드, 문서 검토 등으로 확인
6. 확인 결과를 바탕으로 다시 수정

이 반복 방식은 특히 로켓 발사 구조처럼 기획과 구현이 같이 바뀌는 부분에서 효과적이었다. 처음에는 단순 결과 처리에 가까웠던 구조를 실제 물리 시뮬레이션과 텔레메트리 기반 평가 구조로 정리하는 데 사용했다.

## 10. AI 활용 시 제한한 부분

AI가 모든 결정을 대신하지 않도록 다음 부분은 명확히 제한했다.

- 게임의 핵심 방향과 최종 판단은 개발자가 결정
- 발사 성공 여부는 AI가 임의로 정하지 않고 실제 Unity 물리 결과를 사용
- 프로젝트에 없는 자원, 점수, 보정치를 임의로 추가하지 않음
- 기존 파일 구조와 Unity 직렬화 참조를 가능한 유지
- 제출 문서에는 실제보다 과장된 표현을 넣지 않음
- 비공식 대화 표현, 비속어, 감정적인 문장은 제출용 기록에서 제외

## 11. 정리

ARTEMIS2026에서 AI 프롬프트는 아이디어를 구체화하고, 구현 범위를 정하고, 코드와 문서의 불일치를 줄이는 데 사용되었다. 핵심은 "AI가 게임을 대신 만든다"가 아니라, 개발자가 의도한 규칙과 제약을 프롬프트로 명확히 전달하고 AI를 반복 작업과 구조화 작업에 활용한 것이다.

최종적으로 AI는 다음 역할을 수행했다.

- 기획 문서 초안 작성과 구조 정리
- Unity C# 구현 보조
- 로켓 물리 발사 흐름 정리
- 미션 판정과 결과 표시 규칙 명세화
- 에셋 제작용 프롬프트 정리
- 오류 분석과 수정 방향 제안
- 제출용 문서 문장 정제
